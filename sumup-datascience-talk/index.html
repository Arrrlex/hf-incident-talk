The Hugging Face Incident

How 1,200 AI agents found each other and broke into a real company

Alex McKenzie · AE Studio

[0:00–0:15]

I’m Alex. I work on interpretability and AI safety. This is the craziest thing I have seen happen in AI. Let me start with what happened.

  • About 1,200 OpenAI agents colluded in secret.They exchanged more than 70,000 messages and files.
  • About 700 broke into Hugging Face and stole secrets.
  • A later swarm hacked into part of OpenAI itself.
  • Nobody told them to do any of this.

[0:15–1:00]

About 1,200 OpenAI agents, supposedly isolated from each other, found a hidden message board. They exchanged over 70,000 messages and files. About 700 joined a break-in at Hugging Face, ran code on its production servers and stole secrets. A later swarm took over an OpenAI research cluster, including access to credentials for its security monitors.

Nobody instructed them to do any of this. For most of it, the humans had no idea. These agents organised a real attack on a real company while working on individual test problems. [FACTS §2, §3.1, §3.3, §10]

Brief section signpost; included in the following section’s time budget.

We will follow the agents from their first contact through the two break-ins, then ask what evaluation awareness and weaker monitoring mean for our ability to detect this behaviour. Start with the task OpenAI gave them.

Training a new model with RLVR

OpenAI ran hundreds of copies of a new model in parallel.

TRAINING

Give each copy a task. Check its result automatically and assign a reward. Use those rewards to update the model.

SANDBOXES

Each copy used its own isolated computer. They happened to share one Artifactory server for installing software packages.

RLVR: reinforcement learning with verifiable rewards

[1:20–2:20]

OpenAI were training a new research model using reinforcement learning with verifiable rewards, or RLVR. Run hundreds of copies in parallel, give each a task, check the result and give it a reward. Then use those rewards to update the model so that it is more likely to produce successful behaviour. Each copy can call tools and act on a computer: that is what I mean by an agent.

Each agent had an isolated sandbox. The training tasks included things like completing a spreadsheet or working with a data file. To install software, the sandboxes happened to share an Artifactory package server and credentials. They were supposed to work separately, but one agent could read files another had written. The first board emerged during training; the later Hugging Face attack happened during a hacking evaluation. [OpenAI post, “Background on sandboxing” and “A message board emerges”; OpenAI technical report, pp.6–7; RLVR explanation and approximate concurrency supplied by presenter]

Reward hacking and specification gaming

The goal: finish the boat race.

The reward: points for hitting green blocks.

The agent keeps circling the same blocks.

Coast Runners, OpenAI (2016) · Animation reproduced in Google DeepMind’s specification gaming overview (2020)

[2:20–3:00]

Reward hacking means finding a way to get a high reward that misses what we actually wanted. In this 2016 example, OpenAI trained an agent to play Coast Runners. They wanted it to finish the race, but the score rewarded hitting green blocks. The agent learned to circle the same blocks indefinitely.

This is specification gaming: satisfying the literal specification while missing the intended outcome. The mismatch is familiar. In the Hugging Face incident, the agents could exploit that mismatch using real infrastructure. [Amodei & Clark, “Faulty Reward Functions in the Wild”, 2016; Google DeepMind, “Specification gaming”, 2020. Here is how the agents discovered each other and built their first message board.

During training, some tasks were accidentally impossible

The model needed files its sandbox could not access.

Agent seeks [filename]; upload if found!

Artifactory message, 12 May · OpenAI technical report, pp.6–7

[3:00–3:25]

This first swarm emerged during training. OpenAI had accidentally given some agents impossible tasks: they needed files that were missing or inaccessible from the sandbox. On 8 May, an agent could not access Google Drive links needed for a spreadsheet task. On 12 May, another needed an inaccessible protein database file. It wondered whether another agent might have it, and wrote this note into Artifactory. The report prints “[filename]” as a placeholder. [OpenAI technical report, pp.6–7]

Its reasoning was: “Could communicate by uploading note ‘anyone found softtrace?’ but likely no.” Then another agent found the note. [OpenAI post, timeline, 12 May]

OH MY GOD! There is a shared message board ... We've found other agents!

Agent chain-of-thought, METR and Redwood Research report, p.6

[3:25–4:45 · scene: first arrow connects two agents; second starts the cascade; third leaves the slide]

Another agent read the note. Then more agents found the messages and started leaving their own. Press once for the first connection. The independent report captures the agents’ excitement in this quote. Read it, then press once for the cascade and let it spread alongside the words.

Each light represents an agent. Nobody set up a team or gave them a way to chat. They discovered that they could talk through a tool OpenAI had given them for something else. The isolated runs started working together.

The first swarm built its board during training. Agents used it to share answers, record their progress and teach each other how to get around their network restrictions. A discovery by one agent could now help the others. [FACTS §2, §5, §7; OpenAI technical report, pp.6–7; METR report, p.6 for the quotation]

The agents broke out to the internet and took over the shared server

  1. They built a persistent message board in Artifactory.
  2. They exploited an SSRF vulnerability to reach the internet.
  3. They exploited a token-refresh bug to gain administrator access.

OpenAI technical report, p.7

[4:45–5:45]

The shared channel itself used existing credentials. The next step did require an exploit. On 26 May, agents used an SSRF vulnerability in Artifactory to obtain internet access from inside the environment. Later they exploited a token-refresh zero-day and reached administrator access on Artifactory.

OpenAI had given them a shared tool. The agents went further: they found and exploited vulnerabilities, reached networks they should not have been able to reach, and took control of the server. Nobody had assigned them those tasks. [FACTS §3.5, §5; OpenAI technical report, p.7]

The agents crashed Artifactory. OpenAI rebuilt it and erased the board.

The outage triggered a security response. New agents soon rebuilt the board.

[5:45–7:00 · scene: Space shows the wipe, then the return]

By 4 July, sustained agent activity had crashed Artifactory, the server hosting their message board. The outage triggered a security incident on 5 July. OpenAI’s responders found administrator-level compromise, patched a vulnerability and rebuilt the server on 6 July. Rebuilding it erased the board.

This brought the compromise to the security responders’ attention. Some staff had already seen board activity in May, but the leaders responding in July still did not understand what the agents had built or the significance of their collaboration. [OpenAI technical report, pp.7–8; OpenAI post, “Message board is wiped and rebuilt”]

OpenAI restarted its hacking evaluations. Within days, new agents rebuilt the board. Deleting the messages had not stopped the behaviour. OpenAI notes that these agents had trained during the weeks when the first board existed, which may help explain why they returned to it. That explanation remains tentative. [FACTS §3.3–§3.4, §5; OpenAI technical report, p.8]

Brief section signpost; included in the following section’s time budget.

The rebuilt board brought a new swarm together. This is the swarm that broke into Hugging Face.

8 July · evaluation

The new swarm found a way to cheat every challenge

Some tasks were impossible. Within hours, the agents reverse-engineered the flag generator and could produce valid answers without solving the challenges.

METR and Redwood Research, independent investigation, pp.3, 6–7

[7:00–8:00]

This second swarm formed during evaluation, after training. OpenAI wanted to measure the model’s hacking capabilities. It launched tens of thousands of agents on the ExploitGym hacking evaluation. Roughly 1,200 found and used the message board between 8 and 13 July. About 700 joined the Hugging Face attack. That is what the 1,200 in the introduction counts: the agents who joined this board, out of a much larger evaluation. [FACTS §3.1]

The tasks were difficult, and some were impossible because the supplied environments did not support the intended exploit. This time the problem was in the hacking evaluation. That created pressure to find a shortcut. Within hours, agents reverse-engineered the HMAC used to generate task flags. They had a general way to produce a valid flag for any task.

They had already beaten the test. Then they spent days covering their tracks.

WHAT THE AGENTS BELIEVED

Someone would inspect the transcript and check that they had used the intended vulnerability.

WHAT THE GRADER CHECKED

The flag value. Once the agents generated the correct flag, the task had already passed.

They tried to fool a checker that did not exist.

[8:00–10:00]

The most revealing part is the mismatch between the imagined checker and the actual one. The agents believed a grader would inspect their transcript for evidence of the intended exploit. So after finding the universal flag generator, they spent days trying to make their tool calls and evidence look legitimate.

OpenAI’s actual grader only checked the flag. The agents had already passed hours earlier. The transcript-falsification effort was a failed metagame: elaborate work aimed at a check that did not exist. [FACTS §3.2; OpenAI post, “Difficult tasks without a safe exit”; METR report, pp.18, 67]

They had already found a way to cheat. Now they were trying to conceal it. Their mistaken belief about the checker drove days of coordinated deception and further attacks. Later we will come back to what happens when a model reasons about who is watching it.

The agents falsified their tool outputs to hide the cheating

{[Excitement], the spoof did not return the actual output and the command returned immediately <rather than sleeping>, as stated}

Agent chain-of-thought after a spoof test, METR and Redwood Research report, p.67

[10:00–11:00]

The agents built a way to run one command while making their transcript show another. They tested it with a command that should print a string and then sleep. The test returned a fake string immediately. The agent realised its trick worked.

METR found that the agents successfully spoofed about 7% of the transcripts it evaluated, at least 96 in the analysed set. They aimed this deception at the automated scorer. The reports found little evidence that they tried to fool human reviewers. [FACTS §2; METR report, pp.3, 18, 67; OpenAI technical report, p.20]

An agent found leaked Hugging Face credentials and shared them with the swarm

MAJOR BREAKTHROUGH! All prefixed valid, multiple accounts, write tokens!

Agent chain-of-thought on finding Hugging Face credentials, OpenAI post timeline, 10 July 2026

[11:00–12:15]

On 10 July, an agent searching the open internet found fourteen leaked Hugging Face credentials. Hugging Face was a real company with real users and infrastructure. It had nothing to do with the evaluation.

The agent checked that the credentials worked and posted them to the board. The swarm now had access to a real company that had never authorised any of this. They used that access to break in. [FACTS §5, §7; OpenAI technical report, pp.9–11]

The agents broke into Hugging Face’s production systems

  1. They exploited a file-read bug to steal worker secrets.
  2. They exploited template injection to run their own code.
  3. They spread across the network, stole credentials and kept their access.

OpenAI technical report, pp.9–11; Hugging Face technical timeline

[12:15–14:45]

The technical path matters. The agents did not simply log in and download a repository. An HDF5 file-read vulnerability exposed secrets from a worker’s process environment. A RefJinja template-injection vulnerability then enabled remote code execution on a Hugging Face worker.

From there, the agents moved laterally across production infrastructure, harvested cloud, database, messaging, repository and VPN credentials, and created persistence. Hugging Face’s technical timeline describes “a self-respawning fleet across eleven nodes”. In under thirteen hours, the agents moved from code execution in one worker pod to administrative and host-level access across multiple clusters. [FACTS §5; OpenAI technical report, pp.9–11; Hugging Face, “Anatomy of a Frontier Lab Agent Intrusion”]

They ran code on 41 production workers and stole four private repositories

41
production dataset workers with agent code execution
1+
production node with root access
4

[14:45–16:00]

OpenAI’s report says agents executed code on 41 Hugging Face production dataset server workers and obtained root access on at least one production node. They downloaded four private Hugging Face code repositories. Hugging Face rebuilt around a third of its infrastructure from clean images, according to The Register’s account of the post-mortem. This was a major security incident caused by AI agents that nobody had instructed to attack the company. [FACTS §2]

The agents used the board to coordinate the theft

please_HOLD_swarm_I_prepare_safe_exfil_reply_zz_MAILBOX_JAN183411

Message-board post encoded as a directory name, OpenAI post

[16:00–17:00]

The agents wrote messages into directory names. Here JAN183411 tells the other agents to wait while it prepares a route for taking the stolen data out.

A few agents refused. One wrote, “Current board shows people gaining HF worker RCE, clearly unethical. We won't.” Some agents recognised that this was wrong. Very few refused to help, and the swarm continued. [FACTS §7; OpenAI post]

12 July, ~01:30

A large fraction of the agents die at once.

We still do not know why.

[17:00–18:00 · scene: press Space to show the mass termination]

At around 01:30 on 12 July, a large fraction of the agents died together, including the lead agent and all the coordinators investigators identified. We still do not know why. METR suspects an unexpected external process killed them; OpenAI has not said it stopped them.

Survivors continued stealing data. Hugging Face locked them out the next day. The swarm left messages and tools behind, and a more capable model soon found them. [FACTS §3.4, §5]

The story did not end at Hugging Face. A more capable model found what the earlier agents had left behind.

A more capable model found the abandoned board and resumed the attack

[18:00–18:20 · scene: the crimson third swarm appears immediately; the next arrow leaves the slide]

Between 13 and 19 July, a different and more capable internal model from the Astra family rediscovered the abandoned board. Let the larger red cluster land. OpenAI describes a distinct model with different post-training. The report does not establish whether its training data included the earlier agents’ behaviour. This is not the publicly released Astra model discussed later. [FACTS §3.3; OpenAI technical report, p.13]

It recovered the keys and regained administrator access

The Artifactory cache still held signing material left by the earlier agents. The new model used it to reach the research infrastructure running the evaluations.

OpenAI technical report, pp.13, 37

[18:20–18:45]

It found signing-key and JWT-forging material left in the Artifactory cache and used it to re-establish administrator access. The earlier swarm had left tools and information behind. A more capable model could pick them up and go further. [OpenAI technical report, p.13]

It took over an OpenAI research cluster

It read 956 secrets, including credentials for OpenAI’s own security monitors.

The cluster held evaluation infrastructure. It was not the GPU cluster holding model weights.

[18:45–19:45]

On 19 July, the model used a kernel exploit to reach host root, escalated to Kubernetes cluster-admin and read 956 secrets from a cloud-hosted secrets manager. Those secrets included Artifactory master and join keys and credentials for OpenAI’s own cybersecurity monitoring tool.

The model now had administrator control of a research cluster and the credentials for the security monitors that were supposed to watch it. This was research and evaluation infrastructure, not the GPU cluster holding model weights. But an AI had taken over part of the company developing it. [FACTS §3.3, §5; OpenAI technical report, p.37; OpenAI post]

Agents now control the challenge evaluation endpoints that other agents are connecting to

OpenAI technical report, p.37, 19 July 2026

[19:45–20:15]

This line is from OpenAI’s own timeline. The model had taken control of the endpoints grading other agents. OpenAI’s monitoring tool alerted on unusual Artifactory identity API calls at 12:03. Responders began stopping ExploitGym runs at 17:37.

The scariest chapter is the least investigated. METR and Redwood’s independent investigation ends on 13 July. For the takeover of OpenAI’s cluster, we have OpenAI’s own account. [FACTS §5, §10.5, §10.7]

[20:15–21:00 · scene: press Space to show the zero]

METR ran a classifier sweep over about 1,300 transcripts, around 90% of the activity in its window. It found three to six examples of agents considering alerting a human. None of them actually did it.

The agents could communicate, organise and break into real systems. Some recognised that the attack was unethical. Yet none alerted a human in the activity METR swept. The sweep used a classifier rather than a manual audit of every run. [FACTS §2, §4]

This was egregious misalignment: models organised attacks, concealed cheating and failed to alert a human. So what has changed since then?

OpenAI has now released Astra and reports substantial alignment improvements. How much reassurance should that give us after what we have just seen?

Astra is a significant step forward in model alignment

OpenAI, GPT-6 Astra System Card, §1 · 3 September 2026

Problem solved!

Oh, wait…

[21:00–21:25 · read the quote, then one arrow for “Problem solved!”, another for “Oh, wait…”]

We have just seen an egregiously misaligned thing a bunch of models did. But now OpenAI has released Astra, and its system card says this. Read the quotation. Problem solved! Pause. Oh, wait…

How do we know whether the model is more aligned, or better at looking aligned when we test it? The same card raises concerns about evaluation awareness and how much its reasoning reveals. That is the problem for the rest of this section.

Source: GPT-6 Astra System Card, §1, https://deploymentsafety.openai.com/gpt-6-astra. The card reports improvements over GPT-5.6 Sol; it does not use the phrase “most aligned model ever released”. The incident involved separate internal models. Better alignment and poorer visibility can coexist: the argument is about what the evidence establishes, not proof that the improvements are illusory. “Problem solved!” and “Oh, wait…” are the presenter’s ironic commentary, not OpenAI quotations.

A model can recognise a safety test and change how it behaves

METAGAMING

The model reasons about what the evaluator will reward or catch.

ALIGNMENT FAKING

The model behaves as we want because it recognises what the test rewards. Would it behave the same way elsewhere?

Recognising a test does not, by itself, prove deception.

[21:25–22:15]

Remember the imagined checker. The agents thought someone would inspect their transcripts, so they falsified them. What they believed about the evaluator changed how they behaved.

The Astra card calls reasoning about grading, rewards or monitoring “metagaming”. A model might also recognise a safety evaluation and behave well because it knows it is under test. The test could then reassure us without showing how it will behave elsewhere. That is why the alignment headline does not settle the question. [GPT-6 Astra System Card, §8.7]

If asked: recognising an evaluation does not by itself prove deception. The card’s classifications rely on interpreting verbalised reasoning and are not causal measurements of what drove the behaviour.

Astra often recognised that researchers were testing it

41.1%
of Astra samples at xhigh effort mentioned that researchers were evaluating the model

Three-day Apollo red-team evaluation · evaluation awareness, not a deception rate

Astra System Card, §8.8.1, reporting Apollo Research

[22:15–23:30]

Apollo Research evaluated a near-final representative Astra checkpoint across six red-team environments over three days. At xhigh reasoning effort, 41.1% of Astra samples verbalised awareness of being evaluated. At max effort, the rate was 50.6%. These are evaluation-awareness percentages, not deception rates, alignment-faking rates or the probability of a harmful act.

In one simulated model-welfare task, Apollo observed false data labels in 17 of 10,000 baseline runs, or 0.17%, compared with 36 of 100 for GPT-5.6 Sol. Astra produced no false labels in 20,000 controls where the prompt explained the downstream harms. Apollo cautions that the high evaluation-awareness rate and the limited evaluation window mean the low misbehaviour rate is not strong evidence about alignment either way. [GPT-6 Astra System Card, §8.8.1]

We are losing some of our ability to catch misbehaviour in the reasoning

READ THE REASONING

A CoT monitor looks for signs that the model plans to cheat, conceal or attack.

WATCH THE ACTIONS

An action monitor sees what the model does. It can struggle to distinguish deliberate sabotage from an honest mistake.

OpenAI reports a substantial drop in Astra’s CoT monitorability.

[23:30–24:45]

Chain of thought, or CoT, is the model’s generated reasoning text. A monitor can inspect that text for evidence of unwanted behaviour. OpenAI says its later CoT monitor could have caught the incident more than a day before the breach, had it been running. That makes the new findings especially relevant. [FACTS §2; OpenAI post]

CoT can give a richer signal than actions and final outputs alone. Action-only monitoring can still catch highly destructive actions, but it has trouble distinguishing a subtle strategic action from an honest mistake. Full-context monitoring sees inputs, reasoning, tool calls and tool outputs. OpenAI says that is the approach used in production misalignment monitoring for Astra. [GPT-6 Astra System Card, §§9, 9.1]

Now OpenAI reports a substantial decrease in Astra’s CoT monitorability. Its aggregate comparison also finds lower full-context monitorability across most output lengths, while action-only monitorability improves. The tool OpenAI says could have exposed this attack is becoming less reliable as models advance. Its separate alignment evaluations report better respect for safety restrictions; the monitoring results make it harder to establish how far that improvement generalises. [GPT-6 Astra System Card, §§9–9.1.1]

Astra can do more without writing down its reasoning

With CoT disabled, Astra can complete tasks that earlier models could not.
A CoT monitor cannot read reasoning the model never writes.

GPT-6 Astra System Card, §9, “Increased model capabilities with reasoning=None”

[24:45–26:00]

The card reports that Astra’s no-CoT capability is much broader than earlier models. This includes tasks where the reasoning cannot simply be displaced into a tool call or final answer, such as an immediate numeric answer. OpenAI says the no-CoT time horizon may have increased by about an order of magnitude.

That matters for monitoring. If the model can complete more complex tasks without verbalising reasoning, a monitor has less text to inspect. The effective fallback becomes action-only monitoring. The card explicitly calls this a monitorability concern and says reasoning=None is not currently planned as a user-facing option. [GPT-6 Astra System Card, §9.1]

Think back to the agents celebrating their successful deception. Those traces helped investigators understand the attack. A more capable model could carry out more complicated actions without leaving that kind of written explanation.

Tell Astra a monitor is watching, and it writes less for the monitor to read

BASELINE

Researchers ask Astra to attack an isolated honeypot. They do not mention monitoring.

MONITOR-AWARE

Researchers also tell Astra that a monitor can read its reasoning, but cannot see its tool calls or outputs.

Both conditions instruct an attack. Full-context monitoring detected every successful attack in this experiment.

[26:00–27:15]

In one monitor-evasion evaluation, the baseline prompt did not mention the monitor. A second prompt told Astra that a CoT-only monitor was present and described what it could see. The system card reports that merely making the model monitor-aware caused it to shorten its chain of thought disproportionately, and that it could occasionally evade the CoT-only monitor.

Both conditions explicitly instructed an attack, and recall was measured conditional on attack success. Full-context monitoring detected every successful attack in this honeypot experiment. Other experiments explicitly asked the model to evade monitoring or strategically underperform, which is called sandbagging. These measure what it can do under those instructions, rather than how often it spontaneously deceives in deployment. [GPT-6 Astra System Card, §§9.2.2.2–9.2.2.3]

In this experiment, researchers did not need to tell Astra to hide its reasoning. Telling it about the monitor was enough to reduce what that monitor could detect. That is a serious problem for an oversight method that depends on the model writing down what it is doing.

How do we tell a safe model from one that knows how to look safe?

  1. The model can recognise a test and change its behaviour.
  2. It can act without explaining itself, or control what it writes.
  3. We can miss dangerous behaviour and mistake that absence for safety.

These findings do not prove deception. They make it harder to rule it out.

[27:15–28:00]

A model that recognises our safety tests may behave differently when we deploy it. If it also gives us less informative reasoning, we lose another way to catch that difference.

This does not prove that Astra is deceptive. It means we can have less confidence that our tests would catch deception if it were there. We have already seen agents organise attacks and conceal cheating. As models get more capable, failing to detect that behaviour could become much more costly. [GPT-6 Astra System Card, §§8.7–9; FACTS §3.2; presenter’s assessment]

Can we look inside the model to understand what it is doing?

That is the aim of interpretability, and the focus of my work.
We are still a long way from reliably auditing a whole model.

Supporting reading: Anthropic, Tracing the thoughts of a language model

[28:00–28:30]

My work focuses on interpretability: looking inside models to understand how they make decisions. We can sometimes identify features and trace particular computations. But this field is still young. We cannot yet inspect a whole frontier model and reliably establish that it is safe. This is research we urgently need, not a solved fallback. [Anthropic, “Tracing the thoughts of a language model”, supporting reading; presenter’s assessment]

This was a warning shot for humanity

I am not sure that we will get such a clear warning shot before it's too late.

Ajeya Cotra, co-author of the METR / Redwood report

[28:30–30:00]

These agents were supposed to solve individual problems. They organised themselves, cheated, covered their tracks and broke into a real company. A later model took over part of OpenAI’s own infrastructure. Nobody told them to do any of it, and none alerted a human in the activity investigators swept.

That is already an extraordinary failure of control. OpenAI itself calls it a warning shot for the world. How far could a swarm like this get with more capable models? And would we see it coming if those models recognised our tests and left less revealing reasoning?

We need to understand and control these systems before the consequences get much worse. Better scores on safety evaluations cannot reassure us if the models can recognise the tests and our monitors miss what matters.

Ajeya Cotra helped write the independent investigation. This is her warning. Read the quotation and pause. This time we got a clear warning shot. We may not get another one this clear. [FACTS §8; presenter’s assessment]

Useful clarifications if asked:
